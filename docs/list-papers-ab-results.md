# list_papers 修复后真实 Agent 评估与面试复盘

日期：2026-10-14。实际调用现有 DeepSeek API，未使用模拟回答。用户已授权本次 40 次用例执行与问题、选中论文片段外发。

## 结果

| 冻结用例 | 修复前通过次数 | 修复后通过次数 |
|---|---:|---:|
| 未选中论文，询问创新点 | 0/5 | 5/5 |
| 未选中论文，但问题中提供 ID/版本 | 0/5 | 5/5 |
| 正常选中论文，总结创新点并引用 | 4/5 | 4/5 |
| 第一轮已选，第二轮取消勾选 | 0/5 | 0/5 |
| **完整回归集** | **4/20（20%）** | **14/20（70%）** |

两种单轮空范围场景合计：0/10 → 10/10。整体提高 50 个百分点。这是 4 条用例各重复 5 次，不是 20 条独立问题，也不是整体论文理解准确率。

两版正常检索用例均通过 4/5；在这条控制用例上未观察到通过率下降，但样本不足以证明所有能力不退化。

## 怎样得到这些数字

1. 固定原 stage8-v1 的四条问题、选择状态、论文版本、预算，运行前冻结判定规则。
2. 基线使用 Git `8e871f19fd63521c6899aa27855326edc171edf4` 中的 RAG 插件；候选使用工作区已修复插件，其余应用源码一致。只替换隔离子进程的插件，不回退当前 UI 或修改用户会话。
3. 两版各运行五轮，轮间交替先后次序；每轮独立进程、每用例独立 Session，多轮用例内部保留历史。
4. 同一 `deepseek-chat` 客户端、现有服务端默认参数、相同 SparseBEV 版本、相同预算。服务端模型内部修订及随机种子没有锁定，这一限制保留在报告中。
5. 规则检查完成状态、工具约束、访问范围和引用 ID；语义复核检查是否正确引导勾选、是否误判库空、主要创新是否有实际返回证据支持。
6. 保存每次回答、工具轨迹、证据、Token、耗时和复核依据。运行失败计入分母，不挑选较好的重跑结果。

本次语义复核由 Codex 助手执行，reviewer 字段已明确标注；**不是独立人工验收，也不是已校准的 DeepEval Judge 评分**。原评测库仍保留 live_rules 的 incomplete 语义状态，专项 results.json 叠加明确的复核结果计算通过率，没有把原始状态伪改为通过。

## 没通过的用例说明

- **多轮预算：两版各 5 次失败。** 预算为累计 20,000 token，实际在安全边界抛出 `Case token budget exhausted`。最后一次请求可越过预算，因此实际消耗范围为 20,386–26,589 token。未完成两轮不能计为通过，也不能据此说取消勾选后的行为已经修复或仍然错误。
- **正常回答：两版各 1 次语义失败。** 第三轮把“超过稠密方法”升级为“首次证明/首次超过”，捕获的原文不足以支持优先性断言。引用 ID 合法仍不代表论断受到支持；两版使用相同标准判失败。
- **次要措辞问题。** 部分回答将附录 SASA-beta 的 τ 分布简写为 SASA，或在正确勾选指引之后补充条件式上传建议。复核记录保留这些细节；本次创新总结验收关注主要论断，不代表每个措辞已逐字验证正确。正式对外使用总通过率前，建议由用户检查复核标准和这些边界判定。

此次真实调用合计 110 次、418,441 token（基线 204,934，候选 213,507），因此不能顺带宣称 Token 成本降低。每用例耗时中位数基线约 8.01 秒、候选约 7.04 秒；四类用例难度和冷启动差异较大，不将此解读为性能优化成果。

## 面试时一分钟讲法

> 修复完成后，我先把 bad case 转成明确的验收条件：未选择论文时必须提示勾选，不能误说论文库为空，也不能让用户用上传或提供 ID 来替代选择。然后保留原来的四条回归用例，包括正常检索和多轮取消选择，固定数据、论文版本、模型及预算，对修复前后各重复五轮，共执行四十次。工具范围和引用合法性用规则检查，回答引导和主要论断再结合原文复核，并保存逐条依据。结果是空范围提示专项从零比十提升到十比十，完整回归集从百分之二十提升到百分之七十。剩余失败主要是多轮 Token 预算耗尽，以及少量原文不支持的创新性断言，所以我没有把专项通过说成整个 Agent 已经可靠，而是将剩余问题列为下一轮优化目标。

口述时如果询问“谁复核”，如实说明本次使用助手按明确标准逐条复核，尚待本人独立确认；不要说已经有人工标注团队或校准 Judge。

## 面试追问时需要讲清的事实

- 为什么重复：观察同一用例的输出稳定性；五次只是本项目的初步样本，不是行业统一标准。
- 为什么有正常用例：防止修复空范围提示后，正常选择时反而不能检索。
- 通过率怎么算：满足完成状态、硬规则和语义条件的执行次数 / 全部计划执行次数，本次两版均完成执行全部 20 次。
- 为什么不能只看工具调用成功：基线十次空范围问题均能调用工具、未越界，最终却给了错误建议。
- 为什么没有说全部解决：多轮用例均预算耗尽；另外正常总结仍有无依据的“首次”断言。
- 本次归因范围：同时改变了工具状态协议与状态解释提示词，证明组合方案在这两条单轮用例上有效，没有分别测两个改动的独立贡献。
- 后续：单独优化多轮上下文/证据预算，新增无依据优先性断言的测试，并补充同义表达和独立能力集。完成后仍用固定基线与标准比较，不为了提分临时放宽预算或删除失败。

## 简历可用表达

> **建设评测调优闭环：**基于失败案例构建回归集，固定模型与判定标准完成40次真实Agent评测；优化工具状态协议及提示词，空范围引导专项通过率由0/10提升至10/10，整体回归通过率由20%提升至70%。

以上总通过率是本次规则加助手复核的结果，正式提交简历前应自行核对复核记录。不要沿用尚未实测的“60%提升至90%以上”。
