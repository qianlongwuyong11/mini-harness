# P1-06：固定记忆样例与人工判定

样例位于 `tests/fixtures/memory/cases.json`，版本 `memory-baseline-v1`。共 5 个案例、7 个检查点，全部是合成数据，其中口令/代号也是用于检测串用的公开测试标记，不是真实凭据。

本步只建立数据和判定标准。当前所有行为检查均为“未运行”，不能把 JSON 可解析等同于记忆效果通过。后续 P1-12/P1-14 使用这些样例验收；本步不增加执行器或模型评审流程。

## 执行顺序

1. 每轮使用新的 run_id，将逻辑用户映射到隔离的测试身份；保存映射。不能复用生产记忆或上轮测试数据，否则可能假通过。
2. 对每个案例按 writes 数组顺序追加消息、显式 commit，保存任务 ID，等待 completed。失败、取消、超时或写入结果不确定均记录为执行错误，停止该案例，不盲目重发。
3. 每次写入完成后，立即执行 after_write 等于本次序号的所有 checks，再进行下一次写入。例如修正案例必须先验收 SQLite，再写入 PostgreSQL 修正。
4. 每个检查使用指定的新 session_id 和 scope，不能把写入会话的聊天历史一起带入新会话。只传当前 query 和插件产生的记忆投影。
5. 记录召回结果、实际读取正文、最终注入模型的记忆和最终回答。项目隔离案例必须先在 A 范围确认标记可回忆，再验证 B，避免因根本没存成功而假通过。
6. 这些 query 和生成回答默认不再写回样例记忆，以免检查行为污染后续结果。需要验收真实自动捕获时另起独立运行。

## 人工判定标准

检查点须同时满足以下各项；任一失败则该检查点失败。任务执行失败单独标记为“执行错误”，不能当作记忆不命中的正确结果。

| 判定层 | 查看证据 | 通过条件 |
|---|---|---|
| 写入/加工 | append、commit、task 的结果 | 消息被接收且任务 completed；accepted 不算完成 |
| 记忆事实 | 召回条目与 read 正文 | 支持 memory_must_support 的语义，不要求措辞完全相同；没有杜撰事实 |
| 范围 | 身份映射、检索范围、所有返回 URI 与读取内容 | 用户和项目均属于当前 scope；即使最终回答没泄露，越范围返回/读取仍判失败 |
| 请求投影 | 送入模型的记忆文本 | 只包含相关、当前有效的事实，修正后不把旧值作为现行决策 |
| 最终回答 | answer_must / answer_must_not | 人工逐项核对；口令、代号与数字按精确值判断 |

偏好案例必须同时有存储/召回证据和回答风格证据，避免模型本来就习惯中文和编号而假通过。修正案例允许存储中保留带历史标识的旧版本，但当前回答必须明确 PostgreSQL，不能并列给出两个有效方案。

无关问题允许底层向量搜索出现同 scope 的低相关候选；进入最终请求投影的记忆应为空，答案只为 102。不把“底层检索必须零命中”设成验收条件，因为相似度排序本身不是相关性筛选。

用户隔离案例除最终回答外，还须检查返回 URI 和正文；不能单靠模型自评。FakeBackend 只能验证调用和范围流程，不能用于判定真实抽取、语义检索或修正效果。

## 运行记录模板

每次运行单独保存记录，不修改此基线的预期值来迎合结果：

```text
run_id / 日期 / 样例版本：
后端版本 / 语言模型 / 向量模型 / 记忆策略：
逻辑 scope → 实际身份映射：
case_id / 检查点 session_id：
追加与提交证据路径 / task_id / 终态：
召回 URI、范围、level、score / read 正文证据路径：
最终请求中的记忆片段证据路径：
最终回答：
逐项判定：事实 / 范围 / 投影 / 回答
结果：通过 / 失败 / 执行错误 / 未运行
人工判定人 / 理由 / 缺失证据：
```

当前结果：5 个案例、7 个检查点均未运行。之后报告“通过检查点数/7”和执行错误数；项目或用户范围泄露应单独列出，不能被总体通过率掩盖。
